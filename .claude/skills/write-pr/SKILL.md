# PR 본문 작성 워크플로우

기능을 가리키는 번호는 두 종류다 (`CLAUDE.md` §`data-feature`).

- **기능 ID** `F-0042` — 바뀌지 않는다. 코드의 `data-feature` 속성이 이것을 쓴다.
- **표시 번호** `3.1.2` — 대분류(`1`) · 중분류(`1.3`) · 소분류(`1.3.1`). 기능을 옮기면 바뀐다.

둘의 대응표는 `packages/shared/features/features.json`이다 (`id` ↔ `display_no` ↔ `title`).
판정은 기능 ID로 하고, PR 본문·주석에는 **PR을 쓰는 시점의 표시 번호**를 쓴다.
팀웹(외부 대시보드)이 **소분류별** 진행 상황을 기록하므로 주석에는 소분류만 쓴다.
기준 브랜치는 `develop`이다.

## 1. 입력 수집

1. `git branch --show-current`에서 이슈 번호를 뽑는다 (`feat/60-…` → 60). 못 뽑으면 묻는다.
2. `git diff develop...HEAD --name-only` 와 `git log develop..HEAD --format='%h %s'`로 변경 범위를 본다.
3. `gh issue view {N} --json body -q .body`로 이슈를 읽는다.
   - 본문 끝 `<!-- team-web: … -->`의 번호 = **후보 목록**. 이슈에 적힌 단계는 무시한다.
   - 화면 설명과 API 목록 = 판정 기준.
4. 후보 표시 번호를 `features.json`의 `display_no`로 찾아 기능 ID로 바꾼다.
   주석이 없거나, 소분류가 아닌 번호(`1`, `1.3`)가 있거나, `features.json`에 없는 번호(이슈를 쓴 뒤 번호가 바뀐 경우)가 있으면 짐작하지 말고 묻는다.
   스냅샷이 오래돼 보이면 `features:update`로 갱신해 달라고 요청한다.

## 2. 번호별 판정

이슈는 계획이고 PR은 결과다. **최종 판정은 이 PR의 코드로 한다.**

### 2-1. 판정 대상 찾기

`node apps/web/scripts/feature-impact.mjs develop`을 실행한다. 출력 JSON의 `features[]`가 이 PR이 닿은 기능이다.

| `status`   | 뜻                                                          |
| ---------- | ----------------------------------------------------------- |
| `changed`  | 그 기능 하나에만 귀속되는 변경이 있다                       |
| `possible` | 여러 기능이 같이 쓰는 코드나 ID 여럿을 감싼 범위만 바뀌었다 |

후보 기능마다 `rg 'F-0044' apps/web/src`처럼 그 ID가 달린 요소를 찾고, 그 요소의 하위 트리를 **대상**으로 삼는다.
같은 ID가 여러 요소(Fragment 형제, 여러 페이지)에 달려 있으면 모두 합쳐 대상으로 본다.
페이지·컴포넌트의 루트에 달렸으면 그 파일 전체가 대상이다. import를 따라 `features/`·`shared/`까지 읽는다.
후보 ID가 달린 요소가 없거나 import를 따라갈 수 없으면 판정하지 않고 뺀다.
`unattributed`(어느 기능에도 닿지 않은 변경)는 판정 표 아래에 파일만 나열한다.

### 2-2. 표기

| 조건                                                  | 표기           |
| ----------------------------------------------------- | -------------- |
| 대상이 done 기준을 모두 충족                          | `5.1.1:done`   |
| 대상이 screen 기준을 모두 충족, API 연결이 남음       | `5.1.1:screen` |
| 이 PR이 건드리지 않았거나, 일부만 했거나, 확신이 없음 | 주석에서 뺀다  |

번호는 `features.json`의 현재 `display_no`다. 판정 표에는 `5.1.1 카테고리 전환 (F-0044)`처럼 제목과 기능 ID를 같이 쓴다.

### 2-3. 기준

- **건드렸는지** — 스크립트가 `changed`로 낸 기능만 건드린 것으로 본다. 스크립트는 주석·공백만 바뀐 줄을 이미 뺀다.
  `possible`은 판정하지 않고 주석에서 뺀 뒤 질문으로 돌린다. 여러 소분류가 같이 쓰는 컴포넌트의 사소한 수정이 완료로 기록되는 것을 막기 위해서다.
  `data-feature`만 달거나 옮긴 이관 PR처럼, 바뀐 줄이 표식뿐이면 `changed`라도 done·screen으로 쓰지 않는다.
- **screen 기준 (모두 충족)**
  - 이슈의 화면 설명에 있는 요소가 전부 렌더된다.
  - 이동·토글·열기 같은 상호작용이 실제로 동작한다. 빈 핸들러(`() => {}`)와 `TODO`·`FIXME`가 없다.
  - mock 데이터는 허용한다.
- **done 기준 (screen 기준 + 모두 충족)**
  - 대상에 `MOCK_*`가 없다.
  - 이슈의 API마다 `shared/hooks/` 훅이 그 경로(`'/api/v1/...'`)를 `useApiQuery`·`useApiInfiniteQuery`·`fetchClient`로 부르고 → 대상이 그 훅을 호출한다. 하나라도 못 찾으면 done이 아니다.
  - 로딩·에러·빈 상태를 처리한다.
  - 이슈의 API 중 어느 소분류 몫인지 불분명한 것이 있으면 done으로 쓰지 않는다.
- 틀린 단계는 완료를 잘못 알리므로 **모르면 뺀다.**

## 3. 본문 작성

`.github/pull_request_template.md`의 항목과 순서를 그대로 따른다.

- 개요는 "무엇을 왜"를 쓴다. 작업 내용은 커밋 메시지가 아니라 diff 기준이다.
- 관련 이슈 — `Resolves: #N`을 쓴다. 이 팀은 PR 하나가 이슈 하나를 맡는다.
- 제목 — `[타입] 요약 (#N)` 형식이다. 타입은 브랜치 접두어에서 정한다 (`feat/`→`FEAT`, `fix/`→`FIX`, `refactor/`→`REFACTOR`). 요약은 한국어로 짧게 쓴다.

## 4. 주석

```
<!-- team-web: 5.1.1:done, 5.1.2:screen -->
```

- 한 줄, 본문 **맨 마지막 줄**, 한 번만 쓴다.
- 번호는 PR을 쓰는 시점의 표시 번호(`features.json`의 `display_no`)다. 기능 ID는 주석에 쓰지 않는다.
- 남은 번호가 없으면 주석을 쓰지 않는다.
- `🤖 Generated with …` 줄이 붙는 경우 그 아래, 맨 끝에 둔다.

## 5. 출력

1. 제목 초안 + 본문 초안 (복사하기 쉽게 마크다운 코드블록)
2. 판정 표 — `표시 번호 제목 (기능 ID)` / 스크립트 status / 표기 / 근거(`data-feature` 위치·파일·API)
3. 질문 — 주석에서 뺀 번호마다 이유와 함께 "어디까지 끝났나요?"를 묻는다. 뺀 번호가 없으면 생략한다.

`gh pr create`는 하지 않는다. 사용자가 PR을 만든 뒤 질문에 답하면 그에 맞춰 주석 한 줄을 고쳐 준다.
