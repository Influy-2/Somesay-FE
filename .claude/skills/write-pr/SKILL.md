# PR 본문 작성 워크플로우

기능명세서 번호는 대분류(`1`) · 중분류(`1.3`) · 소분류(`1.3.1`)로 나뉜다.
팀웹(외부 대시보드)이 **소분류별** 진행 상황을 기록하므로 주석에는 소분류만 쓴다.
기준 브랜치는 `develop`이다.

## 1. 입력 수집

1. `git branch --show-current`에서 이슈 번호를 뽑는다 (`feat/60-…` → 60). 못 뽑으면 묻는다.
2. `git diff develop...HEAD --name-only` 와 `git log develop..HEAD --format='%h %s'`로 변경 범위를 본다.
3. `gh issue view {N} --json body -q .body`로 이슈를 읽는다.
   - 본문 끝 `<!-- team-web: … -->`의 번호 = **후보 목록**. 이슈에 적힌 단계는 무시한다.
   - 화면 설명과 API 목록 = 판정 기준.
4. 주석이 없거나 소분류가 아닌 번호(`1`, `1.3`)가 있으면 짐작하지 말고 묻는다. 기능명세서는 레포에 없다.

## 2. 번호별 판정

이슈는 계획이고 PR은 결과다. **최종 판정은 이 PR의 코드로 한다.**

### 2-1. 판정 대상 찾기

`apps/web/src/pages`에서 `rg '@spec'`으로 태그를 모은다 (`CLAUDE.md` §`@spec` 태그).
후보 번호마다 태그 위치를 찾고, 태그가 붙은 컴포넌트와 그 하위 트리를 **대상**으로 삼는다.
페이지 컴포넌트 위 태그면 페이지 전체가 대상이다. import를 따라 `features/`·`shared/`까지 읽는다.
후보 번호의 태그가 없거나 import를 따라갈 수 없으면 판정하지 않고 뺀다.

### 2-2. 표기

| 조건                                                  | 표기           |
| ----------------------------------------------------- | -------------- |
| 대상이 done 기준을 모두 충족                          | `5.1.1:done`   |
| 대상이 screen 기준을 모두 충족, API 연결이 남음       | `5.1.1:screen` |
| 이 PR이 건드리지 않았거나, 일부만 했거나, 확신이 없음 | 주석에서 뺀다  |

### 2-3. 기준

- **건드렸는지** — 주석·공백만 바뀐 파일은 건드린 것으로 보지 않는다. `git diff -w develop...HEAD -- {파일}`의 추가·삭제 줄이 모두 주석(`//` `/* */` `{/* */}`)이면 제외한다. `@spec` 태그만 붙인 완료 페이지가 `done`으로 기록되는 것을 막기 위해서다. 대상의 소분류 전용 파일(`pages/`, `features/`)이 diff에 있어야 한다. `shared/` 파일만 바뀌었으면 건드린 것으로 보지 않는다. 여러 소분류가 같이 쓰는 컴포넌트의 사소한 수정이 완료로 기록되는 것을 막기 위해서다.
- **screen 기준 (모두 충족)**
  - 이슈의 화면 설명에 있는 요소가 전부 렌더된다.
  - 이동·토글·열기 같은 상호작용이 실제로 동작한다. 빈 핸들러(`() => {}`)와 `TODO`·`FIXME`가 없다.
  - mock 데이터는 허용한다.
- **done 기준 (screen 기준 + 모두 충족)**
  - 대상에 `MOCK_*`가 없다.
  - 이슈의 API마다 `packages/shared/src/constants/endpoints.ts` → api → query 훅 → 대상의 호출이 이어진다. 하나라도 못 찾으면 done이 아니다.
  - 로딩·에러·빈 상태를 처리한다.
  - 이슈의 API 중 어느 소분류 몫인지 불분명한 것이 있으면 done으로 쓰지 않는다.
- 틀린 단계는 완료를 잘못 알리므로 **모르면 뺀다.**

## 3. 본문 작성

`.github/pull_request_template.md`의 항목과 순서를 그대로 따른다.

- 개요는 "무엇을 왜"를 쓴다. 작업 내용은 커밋 메시지가 아니라 diff 기준이다.
- 관련 이슈 — `Resolves: #N`을 쓴다. 이 팀은 PR 하나가 이슈 하나를 맡는다.
- 제목 — `[타입] 요약 (#N)` 형식이다. 타입은 브랜치 접두어에서 정한다 (`feat/`→`FEAT`, `fix/`→`FIX`, `refactor/`→`REFACTOR`). 요약은 한국어로 짧게 쓴다.

## 4. 주석

```
<!-- team-web: 5.1.1:done, 5.1.2:screen -->
```

- 한 줄, 본문 **맨 마지막 줄**, 한 번만 쓴다.
- 남은 번호가 없으면 주석을 쓰지 않는다.
- `🤖 Generated with …` 줄이 붙는 경우 그 아래, 맨 끝에 둔다.

## 5. 출력

1. 제목 초안 + 본문 초안 (복사하기 쉽게 마크다운 코드블록)
2. 판정 표 — 번호 / 표기 / 근거(태그 위치·파일·API)
3. 질문 — 주석에서 뺀 번호마다 이유와 함께 "어디까지 끝났나요?"를 묻는다. 뺀 번호가 없으면 생략한다.

`gh pr create`는 하지 않는다. 사용자가 PR을 만든 뒤 질문에 답하면 그에 맞춰 주석 한 줄을 고쳐 준다.
