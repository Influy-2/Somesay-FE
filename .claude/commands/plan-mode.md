# 설계 논의 가이드

코드를 짜기 전에 구조를 함께 고민하는 단계에서 쓴다.
목표는 동작하는 코드가 아니라 **바꾸기 쉬운 코드**다.

규약(폴더·타입·네이밍·상태관리)은 `CLAUDE.md`와 각 패키지의 `CLAUDE.md`를 따른다. 여기서 다시 정의하지 않는다.

## 답변 방식

**구체적인 질문일 때** ("이 컴포넌트 어떻게 설계할까")
→ 질문에 집중한다. 후보 2–3개 + 장단점 + 추천.

**"더 발전시킬 수 있을까" 뉘앙스일 때**
→ 관련 코드를 먼저 읽고, 아래 성장 렌즈로 진단한 뒤 개선점을 짚는다.

### 반드시 지킬 것

- 코드보다 **설계 구조와 근거를 먼저** 답한다
- 후보가 있으면 **후보 A / 후보 B / 추천** 형식으로 제시한다
- trade-off 없이 "이게 좋습니다"로 끝내지 않는다
- 지금 문제가 없는 것을 미리 리팩터링하자고 하지 않는다

### React Native 확장

가능성은 열려 있으나 **확정된 계획은 아니다.** 비용이 큰 결정을 RN 때문에 미리 하지 않는다.
지키는 것은 저비용 제약 하나뿐 — **`packages/shared`에 브라우저 API(`window` `document` `localStorage`)를 넣지 않는다.**

## 후보 비교 포맷

```
### 후보 A — [이름]
- 구조 / 장점 / 단점 / 적합한 상황

### 후보 B — [이름]
- 구조 / 장점 / 단점 / 적합한 상황

### 추천: 후보 B
이유: ...
다만 [조건]이 달라지면 A도 고려할 수 있다.
```

## 설계 질문

**컴포넌트**

- 단일 책임인가? UI와 비즈니스 로직이 섞이지 않았나?
- props가 8개를 넘는가? `children` 합성으로 풀 수 있는가?
- 지금 `shared/`에 올릴 때인가? (3번째 사용처인가)

**상태**

- 서버 상태인가 클라이언트 상태인가?
- 이 상태의 생명주기는 어디까지인가? 더 아래로 내릴 수 있는가?
- 새로고침·뒤로가기·공유에서 살아남아야 하는가? (→ URL)
- Zustand가 정말 필요한가, 상위 컴포넌트 상태로 충분한가?

**변경 비용**

- 이 기능을 **되돌린다면** 몇 개 파일을 건드리는가?
- 반응을 보고 바꿔볼 값이 코드에 박혀 있지 않은가?
- 서버 응답이 바뀌면 어디까지 파급되는가?

**렌더링**

- 불필요한 리렌더가 생기는 지점이 있는가?
- `memo`/`useMemo`/`useCallback`이 실제로 필요한가?
- 리스트 `key`가 안정적인가?

**API·데이터**

- 로딩 / 에러 / 빈 상태를 모두 처리하는가?
- 쿼리키에 응답을 바꾸는 값이 전부 들어갔는가?
- 낙관적 업데이트가 필요한가?

## 안티패턴

**props drilling 3단계 이상** → 상태를 아래로 내리거나 Context/Zustand 검토

**비대한 컴포넌트** — API 호출 + 상태 + 200줄 JSX가 한 파일에
→ 로직을 커스텀 훅으로 추출

**불필요한 전역 상태** — 한 feature 안에서만 쓰는 값을 Zustand에
→ 컴포넌트 상태로 충분하다

**이른 공용화** — 2곳에서 쓴다고 `shared/`로
→ 복제해 두고 3번째를 기다린다. 잘못된 공용화가 복제보다 비싸다

**파생값 저장** — 계산할 수 있는 값을 state·store에
→ 매번 계산한다

**packages/shared에서 브라우저 API** → 추상화하거나 `apps/web`으로

## 성장 렌즈

"더 발전시킬 수 있을까" 질문에서 아래 관점으로 진단한다.

| 관점               | 진단 질문                                                              |
| ------------------ | ---------------------------------------------------------------------- |
| **변경 비용**      | 이걸 바꾸려면 몇 개 파일을 건드리고, 파일마다 무엇을 판단해야 하는가?  |
| **일관성**         | 같은 개념이 코드베이스에서 한 가지 모양인가, 여러 모양인가?            |
| **삭제 용이성**    | 이 기능을 빼려면 무엇이 남는가? feature 밖으로 샌 것이 있는가?         |
| **props drilling** | 상태가 몇 단계를 거치는가? 중간 컴포넌트가 중계만 하는가?              |
| **응집도**         | 변경이 일어날 때 건드릴 파일들이 한 폴더에 모여 있는가?                |
| **상태 소유권**    | 이 상태가 여기 있는 게 맞는가?                                         |
| **추상화 수준**    | 이 컴포넌트가 "무엇을 그리는지"만 알고 "어떻게 가져오는지"는 모르는가? |
| **타입 안전성**    | 런타임에 터질 수 있는 지점이 타입으로 막혀 있는가?                     |
